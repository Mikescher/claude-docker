# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

A Docker-based wrapper around Claude Code itself. The image bundles a developer toolchain (Go, Rust, Node/TS, Python, .NET, Flutter/Dart, Android SDK, PostgreSQL, MongoDB tools, ffmpeg, JDK, Docker CLI, …) plus the Claude Code native binary. The `ccc` script in the repo root is the user-facing entry point: it runs `claude --dangerously-skip-permissions` inside the container with the host's CWD bind-mounted at the **same absolute path** inside the container (so `/home/mike/Code/foo` on the host is `/home/mike/Code/foo` in the container — paths in errors, sourcemaps, and IDE projects line up). The script is meant to be symlinked onto `PATH` so `cd <project> && ccc` "just works".

## Build / run

| Command                                | Purpose                                                       |
|----------------------------------------|---------------------------------------------------------------|
| `make build`                           | Build the `claude-docker` image at the current `latest` Claude Code version |
| `make build CLAUDE_VERSION=2.1.131`    | Pin a specific Claude Code version                            |
| `make build CLAUDE_VERSION=stable`     | Track the stable channel                                      |
| `bash -n ccc`                          | Syntax-check the wrapper                                      |
| `./ccc -h`                             | Show wrapper flags                                            |
| `./ccc --shell`                        | Drop into bash inside the container (skips the claude binary) |

Building **requires the buildx CLI plugin** (`pacman -S docker-buildx`) — see the BuildKit note below. `make build` checks for it and stops if it is missing.

There is no test suite. The smoke-test pattern is `cd /tmp/somewhere && /path/to/ccc --shell <<<'<command>'`.

## Architecture (the parts that span files)

The three files form a small system held together by three contracts:

1. **`claude_version` image LABEL.** Set from the `CLAUDE_VERSION` build-arg. Drives the startup version check in `ccc` (`docker image inspect` vs. `https://downloads.claude.ai/claude-code-releases/latest`). Channel names like `latest`/`stable` are resolved to a concrete `X.Y.Z` **in the Makefile** before being passed to `docker build`, so the LABEL always names a real release.

2. **Host USERNAME/UID/GID build-args.** Passed in by the Makefile from `id -un`/`id -u`/`id -g`. The container user is created with the host's name and IDs so files written into the bind-mounted workspace and caches end up owned correctly on the host — no chown dance needed — and `$HOME` inside the container is `/home/<host-username>`, matching the host. Override with `make build USERNAME=foo` if needed. `ccc` resolves the in-container home by reading `Config.User` from the image, so old images built before this change keep working until rebuild.

3. **State mounts.** `~/.claude` (sessions, plugins, settings) and `~/.claude.json` (per-project state) are the two pieces of Claude Code state shared host↔container. The wrapper also forwards `~/.gitconfig` and `~/.ssh` (read-only) — if a `~/.gitconfig-ccc` exists on the host it wins and is mounted as the container's `~/.gitconfig`, so the container can carry its own git identity/config — and the language caches (Go modules/build, npm, pip, optional `uv`/`cargo`/`.nuget`). Hosts paths that don't exist are silently skipped — Docker is not allowed to auto-create them as root. Claude's per-project temp dir (`/tmp/claude-<uid>/<cwd-slug>` — scratchpads, background-task output) is also bind-mounted from the host's `$TMPDIR` (created there if missing), on top of a user-owned tmpfs at `/tmp/claude-<uid>` so claude can still create sibling dirs; `--no-claude-temp` turns it off.

**`.claude-docker` project config (split across ccc and the entrypoint).** An optional JSON file in the workdir. `ccc` reads `automount` / `automount-ro` (a list of dirs or a single string, relative to the workdir; absolute and `~/` paths work too) and adds them like `--mount` / `--mount-ro` after **one** `[Y/n]` for the whole list (default yes; with no terminal on stdin/stderr they are mounted without asking). Missing dirs are skipped with a stderr line; malformed JSON or non-string entries abort. Entries already covered are dropped silently: the workdir mount itself and any `--mount`/`--mount-ro` of the same dir (docker rejects a duplicate target), and a rw dir under the workdir mount — a ro one under it stays, as a read-only overlay. The host's `jq` is used when present, otherwise the image's via `docker run --entrypoint jq` (the file goes in on stdin). `ccc-entrypoint` reads `node-version` / `java-version` from the same file with the image's `jq`; they take precedence over `.nvmrc` / `.java-version` and go through the same nvm / JDK-matching code.

**Docker socket passthrough.** `/var/run/docker.sock` is bind-mounted from host to container when present, and the container user is granted the socket's GID at runtime via `--group-add` (the host docker GID varies, so it can't be baked into the image). This is *sibling-container DinD*: `docker` calls inside `ccc` go to the **host's** daemon, so any sibling container that needs a bind mount expects a **host** path — which is fine in practice because the wrapper's "host path == container path" workspace mount means workspace paths pass through transparently.

**`ccc-entrypoint` runs before every command.** The image sets `ENTRYPOINT ["/usr/local/bin/ccc-entrypoint"]`, so both `claude` (the CMD) and `bash -l` (shell mode) are wrapped. The script is the single bootstrap point: if a `.nvmrc` is present in the workdir at startup it sources nvm and runs `nvm install`, if a `.java-version` is present it points `JAVA_HOME`/`PATH` at the matching JDK under `/usr/lib/jvm` (matched on major version: `25`, `21`, `17`, `1.8`, `25.0.3`, … → `java-<major>-*`, optionally vendor-qualified — `temurin-25`/`openjdk-25` — to force a specific build when a major has both; on no match it prints an error and pauses 2s before falling back to the system default; `.claude-docker`'s `node-version`/`java-version` outrank both files, see above), and it patches the marketplace-cached `chrome-devtools-mcp` plugin config to add `--browser-url=http://127.0.0.1:9222` (re-applied each start because plugin updates wipe the cache; the in-container Chrome path doesn't work, so the MCP attaches to a host Chrome over `--network host` — see the chrome-on-demand contract below). In sessions with the emulator relay it also registers mobile-mcp for `claude` (see below). Anything that needs to happen on every container start regardless of mode belongs here. The path is fixed (not under `$HOME`) because `ENTRYPOINT`'s exec form does not substitute build-args.

**Chrome on demand (the ccc↔Dockerfile port contract).** The chrome-devtools MCP is always registered, and Chrome is started *lazily* by the wrapper rather than by a flag. `ccc` puts a `socat` broker on `127.0.0.1:9222` — the address `ccc-entrypoint` patches into the plugin config — with `fork` and `EXEC:<ccc> --internal-chrome-relay`, so the script re-invokes *itself* once per accepted connection; the relay ensures a host Chrome is up on **9223** and splices the connection through. The MCP connects only when a tool needs the browser, so the first chrome tool call is what opens the window. Only that first `/json/version` request crosses the broker: it answers with a `ws://127.0.0.1:9223/…` URL that puppeteer dials directly (which is why this needs host networking, and why `--net` disables the feature). Chrome's DevTools `Host` check accepts the rewritten `127.0.0.1:9222` header because it only requires an IP literal and ignores the port. Both Chrome and the broker are `setsid`'d so they survive Ctrl-C and outlive the session — the next `ccc` finds 9222 busy and reuses them. Chrome's profile is persistent (`~/.cache/ccc-chrome/profile-<port>`) and seeded once, because a *fresh* profile is what produces the first-run, metrics-consent, search-engine-choice and keyring-unlock modals that otherwise sit in front of the window; the launch flags cover the rest. `--chrome` now only means "start it now", `--no-chrome` skips the broker, and every unmet precondition (no socat, no Chrome, `--net`, a space in the script path) degrades to one stderr line with the session otherwise intact.

**Android emulators on demand (the ccc↔Dockerfile relay contract).** Emulators run on the **host**, which has the AVDs, KVM, the GPU and the desktop the window opens on; the image has no emulator binary. adb, flutter and mobile-mcp in the container use the host's adb server on `127.0.0.1:5037` over host networking: `install`/`push`/`screencap` stream through the client, and `adb forward` (flutter's VM-service connection, mobile-mcp's device agent) listens on the shared loopback. Only *starting* an emulator needs the host, through a relay: per session `ccc` makes a `mktemp -d` dir, runs `socat UNIX-LISTEN:<dir>/sock,fork EXEC:<ccc> --internal-android-relay` in the background, mounts the **directory** at `/run/ccc-android` (the socket may not exist yet when docker resolves mounts, and a missing source would be created root-owned) and kills the listener on exit. Protocol: one request line (`list`, `version`, `adb-server`, `start <avd> [flags]`), answered by lines tagged `o ` (stdout) / `e ` (stderr) and a final `x <rc>`. `start` checks the AVD against `emulator -list-avds`, starts the host adb server from the SDK's own platform-tools (Arch's `android-tools` adb can be broken), returns the serial of an already running instance (matched via `adb emu avd name`), otherwise picks a free even console port in 5554–5584 via procfs, `setsid`s the emulator (it outlives the session like Chrome; log in `~/.cache/ccc-android/<avd>.log`) and returns once adb lists it. Flags are an **allow-list** (`-no-window`, snapshot/boot-anim/audio flags, `-read-only`, `-wipe-data`, and `-gpu`/`-memory`/`-cores`/`-port` with validated values) because the socket is a command channel into the host and the emulator CLI can run host programs (`-qemu`, `-shell`, tap scripts) and open host paths; `CCC_EMULATOR_ARGS` on the host is trusted and appended as is. Windowed launches set `QT_QPA_PLATFORM=xcb` (the emulator's bundled Qt has no wayland plugin); without `DISPLAY` the relay starts headless and says so. The host SDK is the first of `$CCC_ANDROID_SDK`, `$ANDROID_HOME`, `$ANDROID_SDK_ROOT`, `~/Android/Sdk`, `/opt/android/sdk`, `/opt/android-sdk` that has `emulator/emulator`. Unix socket paths are limited to 108 bytes, so a very long `$TMPDIR` breaks the listener.

The image side is `/usr/local/bin/ccc-emulator` (`list`/`start`/`stop`/`status`/`adb-server`; `start` also waits for `sys.boot_completed`), symlinked as `emulator` on `PATH` and at `$ANDROID_HOME/emulator/emulator`, where flutter looks. Called `emulator`, it answers what flutter runs: `-list-avds`, `-version`, and `-avd ID [-no-snapshot-load]` with exit 0 meaning launched. Its socket client is python3, so the image needs no socat. `ccc` adds around it: `ADB_SERVER_SOCKET=tcp:127.0.0.1:5037` whenever host networking is on — adb treats `localhost` as a local server it may fork and `127.0.0.1` as a remote one, so the container never starts a server of its own, which would take the host's 5037, die with the container and present the image's adbkey instead of the one the host's devices trust; the host's `~/.emulator_console_auth_token` read-only (adb reads it client-side for `adb emu`); `~/.android/avd` read-only (only for flutter's display names); and, in every session, `~/.android/debug.keystore` read-only (otherwise each container signs with a fresh debug key and reinstalling fails with `INSTALL_FAILED_UPDATE_INCOMPATIBLE`). `--no-android` skips the relay, a host without an SDK skips it silently, and `--net`, missing socat or an unsafe path degrade to one stderr line.

**mobile-mcp** (`@mobilenext/mobile-mcp`, npm global) gives Claude screenshots, the element tree and tap/type/swipe on those devices. `ccc-entrypoint` adds `--mcp-config /etc/ccc/mobile-mcp.json` to `claude` only when `/run/ccc-android` is mounted and the next argument is an option — the flag is variadic and would swallow a prompt. It is not in `/etc/claude-code/managed-mcp.json` because that file takes exclusive control and would disable the user's own MCP servers. The config runs it on `/usr/bin/node` (a project `.nvmrc` may select a node older than its `>= 20`) with `MOBILEMCP_DISABLE_TELEMETRY=1`. It names some emulators by AVD name rather than serial; tools take the id from `mobile_list_available_devices`.

**Managed CLAUDE.md.** `/etc/claude-code/CLAUDE.md` is Claude Code's managed-policy memory: every claude session in the container loads it alongside the user's and the project's CLAUDE.md. It tells Claude what the container offers (sibling docker, host networking, the chrome MCP, `ccc-emulator`). It costs context in every session, so keep it short.

**Default network is `--network host`.** Host services bound to `127.0.0.1` (e.g. MongoDB on 27017) are reachable as `localhost` from inside the container without further config. `--net` switches to bridge networking and adds `host.docker.internal:host-gateway`.

**Git-worktree auto parent-mount.** A worktree checkout has a `.git` *file* (not a dir) reading `gitdir: <path>`, where `<path>` is the real gitdir living under the main checkout (e.g. `repo/master/.git/worktrees/wt-4`). Mounting only the worktree dir would leave git broken inside the container, so `ccc` reads that `.git` file at startup and, when the gitdir resolves to something under the workdir's parent (the usual `repo/<worktree>` layout), flips on `--mount-parent` automatically so the gitdir comes along. It's gated on the gitdir actually existing under the parent — if it lives elsewhere a parent mount wouldn't reach it, so the wrapper leaves the mount alone. Relative `gitdir:` targets are resolved against the workdir; canonical paths are compared so symlinks don't cause false misses.

**Update model is rebuild, not self-update.** The image sets `DISABLE_AUTOUPDATER=1`. Upgrading Claude Code means rerunning `make build`; the version-check prompt in `ccc` is the nudge.

## Things to know when editing

- **The build requires BuildKit.** `ccc-entrypoint` and the `notify-send` shim are written with `RUN cat > <file> <<'EOF'` heredocs, which only the BuildKit frontend parses. `docker build` uses BuildKit only when the **buildx CLI plugin** is installed — `DOCKER_BUILDKIT=1` is not a substitute (it errors out with "buildx component is missing"). Under the legacy builder the failure is silent and nasty: the Dockerfile parser swallows the heredoc body but `sh` gets an unterminated redirect, so both scripts are created **empty**, the build reports success, and the damage only surfaces at run time as `exec /usr/local/bin/ccc-entrypoint: exec format error` (exec of a 0-byte file). `make build` guards on `docker buildx version` for exactly this reason — if you add more generated scripts, keep using heredocs, but don't drop the guard.
- **Dockerfile layer order is load-bearing** for cache reuse: pacman → mongo tools (still root) → `useradd` → write `/usr/local/bin/ccc-entrypoint` (still root) → `USER ${USERNAME}` → npm / go / pipx → Android SDK / Flutter → the Android relay block (mobile-mcp, then a `USER root` stretch for `ccc-emulator`, `/etc/ccc` and `/etc/claude-code`, then back to the user) → claude install. Pacman is the heaviest layer; do not move language-tool installs above it. Anything that depends on the user's `$HOME` must come after the `USER ${USERNAME}` switch.
- **`PATH` precedence in the image** is `~/.npm-global/bin` → `~/.local/bin` → `~/go/bin` → `~/.cargo/bin` → system. So `npm i -g`, `pipx install`, `go install`, and `cargo install` all land on `PATH` automatically; pacman packages need no extra setup. Rust itself (`rustc`/`cargo`/`clippy`/`rustfmt`) is the pacman `rust` package in `/usr/bin`, deliberately not rustup — a rustup install puts its toolchain shims in `~/.cargo/bin`, which the runtime `~/.cargo` cache mount would shadow.
- **MongoDB tools** are fetched as a tarball from `fastdl.mongodb.org` because Arch's repos don't carry them. The `rhel88-x86_64` build is the one that works on Arch; the older `rhel80` URLs now 404. Bump `MONGO_TOOLS_VERSION` in the Dockerfile to update.
- **Version-check timeout in `ccc` is intentionally 1 s.** The endpoint typically responds in ~230 ms; raising the timeout regresses cold-start. The check also no-ops on a non-TTY stdin so piped invocations stay clean.
- **Empty-array expansion in `ccc`** uses `${forwarded_args[@]+"${forwarded_args[@]}"}`. The `+` form is required because of `set -u` — don't simplify it.
- **`~/.claude/settings.json` overlay.** The host's settings file is mounted on top of the container's empty `~/.claude`, so any env vars set there take effect inside. The Dockerfile's `ENV DISABLE_AUTOUPDATER=1` is a belt-and-suspenders default for users without that key.
- **Flutter targets Android and Linux desktop.** The Android command-line tools, `platform-tools` (adb), and the latest two platform/build-tools are installed under `$ANDROID_HOME` (`~/Android/Sdk`); the Flutter stable SDK lives at `~/flutter` with the Dart SDK + Android engine precached. Both are under `$HOME` (not `/opt`) because `flutter` and `sdkmanager` write into their own trees at runtime, which a root-owned install would forbid. The image's default JDK is the newest `jdk-openjdk`, which the Android Gradle Plugin doesn't support, so `jdk17-openjdk` is installed alongside it and Flutter is pointed at it via `flutter config --jdk-dir` (the system default is left untouched, per the ivy note below). The cmdline-tools download URL carries an **exact build number** (`ANDROID_CMDLINE_TOOLS_VERSION`); bump it from the newest entry in `repository2-3.xml`. The Linux-desktop target's toolchain deps (`clang`, `cmake`, `ninja`, `gtk3`, `mesa-utils`) are in the pacman layer; the **web** target is not wired up (no Chrome in the image, but the host's `/opt/google/chrome` is bind-mounted read-only when present, so `CHROME_EXECUTABLE=/opt/google/chrome/chrome` over `--network host` is the way in). No emulator runs in the container: emulators and USB devices are the host's, reached through its adb server (see Android emulators on demand). Gradle (`~/.gradle`) and pub (`~/.pub-cache`) caches are forwarded by `ccc` like the other language caches.
- **nvm is installed but inert by default.** The toolchain ships system Node from pacman; `node`/`npm` resolve to that. nvm is sourced only by `ccc-entrypoint` when the workdir has a `.nvmrc` or a `.claude-docker` `node-version` (and by `.bashrc` so the `nvm` function is reachable interactively in shell mode). Both call sites `unset NPM_CONFIG_PREFIX` first because nvm refuses to load otherwise — the pre-installed npm globals stay reachable because `~/.npm-global/bin` is hard-coded into `PATH`, independent of the prefix var.
